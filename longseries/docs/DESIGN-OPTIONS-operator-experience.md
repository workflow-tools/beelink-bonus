# Design options — the operator experience

**Status: nothing here is decided.** This is a triage document, not a plan.
Four designers were given the same brief and opposed stances — CLI-first and
dependency-free; a static generator rather than a server; push artefacts and
have no surface at all; subtract, because most of the scope should not be
built — and one critic then attacked all four against the code. Where they
split, both sides are recorded below rather than resolved. Where the critic
killed something, it says so and says why.

The reader is expected to overrule this freely. Every recommendation carries
a confidence level and the evidence that would flip it, precisely so that
disagreeing is cheap.

**Context that constrains everything.** 105 passing tests, three
live-verified sources, and **zero captures on any host that exists**. ADR-001
Q7 step 2 — provision the VPS, enable backups, create the checks,
`docker compose up -d` — is owner work that has never happened. The register
prices this option at `setup_hours: 0`, `monthly_eur: 5`, `review_date:
2026-11-30`, station 2a (buyers now) **FAIL**, station 6 (validation) **not
started**. Any proposal spending thirty hours of build silently rewrites the
premium that justified collecting at all.

---

## 1. Consensus — the closest thing to safe

All four designers, from four opposed stances, independently reached these.
The critic upheld every one.

- **No admin backend.** No listening socket on the collector, no auth, no
  sessions, no TLS to renew, no framework on a CVE tempo, no second copy of
  state that can disagree with the store. Even the designer arguing *for* a
  page refused to build a server for it.
- **healthchecks.io stays the only automatic alerting path.** regwatch's
  `notify.py` stays unwired (ADR Q4 held). One designer defected by adding an
  email API; the critic ruled that a credential and a billing relationship on
  the host holding the only copy of the asset, with no dead-man's switch of
  its own, is not a small addition.
- **No database.** Files remain the store; DuckDB stays a query engine over
  them (ADR Q5 held). `index.jsonl` is correct at 10³ rows.
- **No web form for adding a source** — a form invites guessing `polarity`,
  the one config field whose silent wrongness inverts the entire series.
- **Write the owed `ops/` as systemd units and shell, not a Python
  subsystem**: a pull timer and a host-heartbeat timer, each with its own
  check. Nobody wants fleet tooling for two hosts.
- **Defer gold and any API** until a named buyer asks (ADR Q5, Q7 step 3).
- **Make the machine say the `review_date`.** Four designs that agree on
  almost nothing converged on the same two-hour change. The critic called it
  the safest available decision. *How* it should fire is still open — see D5.

## 2. The open decisions

### D1 — Should any web or visual surface exist, and where would it run?

**Options.** (a) None: CLI plus push. 0 h. (b) A generator: `longseries
report` as a pure function of the store writing `report.md`, no process, no
port. 6–8 h. (c) (b) plus an HTML twin. +4 h. (d) A read-only
`python -m http.server` on `127.0.0.1` on the Beelink over Tailscale. +1 h on
(c). (e) A real backend. 20–40 h plus indefinite patching.

**Tradeoffs.** (a) leaves nothing to browse the moment the series becomes
interesting — which is also the cheapest evidence about whether the data has
value. (b) cannot be exploited (never listening), cannot corrupt the archive
(read-only over the store), and can rot for a year costing nothing but the
page. (c) is where the critic found the flaw: **GitHub serves a repository's
`.html` as source text, not a rendered page.** Only markdown renders on a
phone, so the HTML half — the fleet band, the sparklines, and the staleness
JavaScript that stops a dead collector's last page looking plausible forever
— is unreachable on the only device it was designed for. (e) was killed
unanimously.

**Failure modes.** (b) generated *inside the poll* races three per-source
containers sharing one data root, and a `report/` directory under
`$LONGSERIES_DATA` acquires state the pull timer's `rsync --ignore-existing`
copies once and never updates — permanently stale, wedged inside the replica
the ADR requires to stay clean. (a)'s failure mode is that the first buyer
conversation has nothing to point at.

**Recommendation:** (b), markdown only, generated by its own timer, written
**outside** `$LONGSERIES_DATA`. Defer HTML. **Confidence: medium.**

**What would change it:** a named person other than the owner asking to look
at the series, or a buyer conversation where a link converts and an
attachment does not. Then (c)+(d) becomes right and the refusal was a slogan.

### D2 — What is the smallest sufficient command set?

Today: `validate poll schedule extract series show`. Every one needs a YAML
path; every one but `validate` needs `--data`, `required=True`, with no env
default. That friction — not the verb count — is why `show` is unused.

**Options.** (a) Keep the six; fix the defaults (`LONGSERIES_DATA` from env,
sources default to a glob, no source argument means all sources). ~4 h.
(b) Reallocate to six: machine-facing `poll/schedule/extract`, human-facing
`status/changes/add`, folding `show` and `validate` away and renaming
`series`. ~6 h plus doc churn. (c) Keep adding verbs — `doctor`, `digest`,
`new-source`, `report`, `verify` — and reach eleven.

**The split.** Two designers wanted the fold; two wanted narrow additions.
The fold's argument is that a separate `doctor` splits the fault path, so
`status` should escalate into diagnosis by itself — a good instinct for one
operator and the wrong shape for two, since a team wants a boring stable
status and a separate deep tool whose output can be pasted.

**Failure modes.** (a) leaves the fleet question costing six invocations
across two machines. (b) invalidates the README, the ADR and the registry's
worked commands for a single user's convenience. (c) produces a CLI nobody
can hold in their head after eleven months away.

**Recommendation:** (a), plus exactly two new verbs over the year — `verify`
(re-hash blobs against their filenames) and `report` — and **zero renames**.
**Confidence: high** on the defaults, **medium** on refusing the rename.

**What would change it:** a second operator. Then (b) is right.

### D3 — How should "what changed" be surfaced, and in what form?

**Correct the premise first.** `render_markdown()` already emits Transitions,
Appeared, Disappeared and Restatements *before* the latest-state table, and
`build_series()` computes all four. One design priced eight hours against a
gap that does not exist. What is missing is **delivery and scope**, not
computation.

**The two real gaps, both cheap.** `build_series()` recomputes over the whole
silver history and keeps no cursor, so anything firing on "a transition
exists" fires **every poll, forever** after the first (~1 h for a seen-set; a
precondition for D4). And a source with no parser — 50Hertz, TenneT — renders
as *nothing changed*: US-04's failure mode one layer up, a collector
reporting success while returning zero rows. A bronze section ("3 new blobs,
no parser") is ~2 h.

**Options.** (a) Nothing; run `series` at a terminal. (b) Add a `--since`
window plus the bronze section plus the cursor. ~4–6 h. (c) A timeline view
(see D1). (d) Cross-publisher diffs — blocked on gold, which has no reviewed
crosswalk; a view implying comparability no reviewed file supports is worse
than no view.

**Recommendation:** (b). Do not build a timeline until edition two exists and
shows what a diff actually looks like on real data. **Confidence: high** on
the cursor and the bronze section, **medium** on the `--since` window.

**What would change it:** the second Amprion edition landing. Everything
about presentation should be decided against it, not against fixtures.

### D4 — Should artefacts be pushed, or wait to be visited?

**Options.** (a) Wait. (b) Push down the existing healthchecks `/fail`
channel — free, no credential, no new dependency, and the ping body already
carries up to 100 KB. (c) Push by email API or a git deploy key — formats
properly, reaches a phone, and puts a credential plus a billing relationship
on the collector host. (d) Push as the body of a **success** ping.

**(d) does not work.** healthchecks notifies on status *transitions*, not on
pings; a success ping to a healthy check sends no email and no push. The
digest would sit in the healthchecks web UI waiting to be visited — exactly
the pull surface its own design forbade. This was one design's flagship
feature and it was ruled WRONG.

**The real cost of (b).** It conflates "something is wrong" with "something
is interesting", and — more seriously — it pushes findings down the same
latch that carries liveness. See §4, gap 1: that is how the dead-man's switch
dies. (b) is only safe *after* the liveness/findings split.

**The real cost of (c).** Neither a dormant free-tier email account nor a
rotated deploy key has a watchdog of its own; month seven's silent suspension
looks exactly like a quiet month.

**Recommendation:** (b), after the split, with the cursor from D3.
**Confidence: high** on rejecting (d), **medium-high** on (b) over (c).

**What would change it:** the first real transition arriving as a truncated
or unreadable `/fail` body on a phone. Then (c) earns its credential.

### D5 — Should the register's review dates generate their own reminders?

All four said yes. The open question is **what fires it**, and the panel
skipped the honest baseline.

**Options.** (a) A calendar entry in his phone for 2026-11-30. Five minutes,
zero code, works today when no host exists, and cannot be muted by a channel
he stops reading. (b) A line printed by `show`/`status` — seen only if
visited, i.e. never. (c) A `/fail` ping from a registry timer at T-30 and
T-0, silenced by a `history:` entry dated after `review_date`. ~2 h.

**Failure modes.** (a) is invisible to the machine and dies with the phone.
(b) is theatre. (c) nags about a review done in his head and not written
down, and teaches him to skip the one section with a deadline in it.

**Recommendation:** do **(a) today** — it costs five minutes and does not
depend on a host that does not exist — and add (c) **twice only**, at T-30
and T-0. **Confidence: high** that something must exist; **medium** that (c)
is worth its two hours on top of (a).

**What would change it:** whether the 2026-11-30 review actually happens. If
a calendar entry produces it, (c) is redundant forever. And see §4 gap 7:
nobody has defined what a *kill* does.

### D6 — Should a repair channel exist that works from a phone?

Nobody designed this; the critic found it. Every design routes alerts to a
phone and none gives him anything to do with one. Repairing
`LANDING_VANISHED` means editing a YAML — a laptop and an ssh session he will
not have mid-relocation.

**It is 90% built already.** `cmd_poll` calls `_load(args.source)` on every
iteration of the schedule loop, and `sources/` is a mounted volume, so an
edited file takes effect on the next poll with **no restart**.

**Options.** (a) No: repair needs a laptop. 0 h, and weeks of a dead
collector during a move. (b) A host-side `git pull` timer into `sources/`, so
a GitHub web edit from a phone repairs a collector within a day. ~3 h.
(c) (b) with a gate: the timer runs `validate` on the incoming tree and
refuses to swap it in if it fails. ~4 h.

**Blocker for all of them, and a live bug regardless.** `_load()` calls
`sys.exit(1)` on a `ConfigError`; `cmd_schedule`'s loop catches
`except Exception`, which does **not** catch `SystemExit`; and the `Heartbeat`
is constructed *after* the config loads. So a typo — pushed from a phone or
typed on a laptop — exits the container into a `restart: unless-stopped` loop
that never pings, and the only signal is a missing ping a day later. ~1 h to
fix.

**Recommendation:** fix the `SystemExit` hole now regardless; build (c) only
after the host exists and one real repair has been done by hand.
**Confidence: medium.** This is the most interesting unbuilt idea here and
the least validated.

**What would change it:** the first `LANDING_VANISHED` in the wild, and where
he is when it fires.

## 4. Do not build

- **Any admin backend, or any listening socket on the VPS.** Unanimous.
- **A digest delivered as a healthchecks *success* ping.** It does not
  arrive (D4). Killed by the critic.
- **`restic` offsite backup tonight.** Correct item, wrong date: it protects
  zero bytes today, on a host that does not exist, under an ADR that already
  specifies provider backups plus a second replica. Killed as sequenced;
  becomes the first thing to build at roughly ninety captures.
- **A preflight that refuses to *collect* when the watchdog is
  unconfigured.** Under `restart: unless-stopped` with no log cap that is a
  crash loop, and it trades the irreproducible asset for the alarm watching
  it. Warn loudly, fail-ping, keep collecting. Killed by the critic.
- **Renaming `series` and folding `show`/`validate`** (D2).
- **A local-model prose appendix in any artefact.** Self-condemned by its own
  designer; a hallucinated megawatt figure quoted to a buyer spends the
  credibility of the series on a sentence nobody needed.
- **HTML in a git repo expecting GitHub to render it** (D1).
- **A weekly digest** (nothing to digest), **charts before four editions**, a
  **TUI**, **completions**, **self-update**, **Prometheus/Grafana**, a
  **headless-browser tier** for TenneT (a licence question, not an
  engineering one), **blob pruning**, an **installer**, and **DOM
  canonicalisation** (deferred in Q6, still not needed).

> **Overridden 2026-09-12 (owner): the installer was built** — `longseries
> setup`, one command inside the image (`docker compose run --rm setup`). The
> subtract designer's reason — "real; irrelevant at three sources and one poll
> a day" — priced it by how often it runs. The owner's constraint is attention,
> not skill: the five-command install had not happened in the week since this
> document, and the healthchecks step was the part needing a human. The
> critic's ruling above still stands: `setup` never gates *collection* on the
> watchdog — a missing key is a capital-letters UNMONITORED, not a refusal.
> The one gate added is the data-root marker (FAILURE-MODES #12), which
> protects the asset, not the alarm.

## 5. The gaps nobody designed for — year-one operational risk

Probably the most valuable section here — all found by reading the code
adversarially, not by arguing about interfaces.

1. **A findings alert permanently disables the dead-man's switch.**
   `run_with_heartbeat` fails the check on any P0/P1. `STALE` and
   `ZERO_NEW_FILES` derive from `last_change_at`, so once true they stay true
   every poll; the check latches down — and **a check already down cannot
   signal a missing ping**. A quiet publisher silently disarms the only thing
   that distinguishes a working collector from a dead one. Fix: two checks
   per source, one that always succeeds at the end of a poll, one that only
   ever fails.
2. **A truncated index line bricks a source forever.** `_append_index` is an
   unguarded append; `_iter_index` calls `json.loads(line)` with no `try`;
   and `save()` calls `versions()` — hence `_iter_index` — on *every* payload.
   One ENOSPC mid-write and every subsequent poll of that source raises.
   Total failure, not degraded read.
3. **A config error escapes the schedule loop** (D6).
4. **Docker logs, not bronze, fill the disk.** `compose.yaml` sets no
   `logging:` options on three `restart: unless-stopped` services. ADR Q3's
   "alert under 2 GB free" treats the symptom.
5. **Landing and `robots.txt` snapshots are stored in full every poll,
   undeduplicated.** `write_snapshot` does no content addressing. 50Hertz's
   landing page is ~344 KB, and its raw bytes differ every fetch — so it also
   mints a fresh blob daily. That single source is ~250 MB/year of near-identical
   copies.
6. **The failure path discards its own evidence.** `poll()` returns before
   `write_snapshot` on `LandingVanished` or any `HTTPError`, so no
   `landing.html` is written. When a TenneT-style challenge wall appears, the
   manifest keeps the status code and throws away the body that says *which
   kind* of wall it was — which is also the entire mitigation for "a source
   goes behind a login": record the date and the shape, re-screen the option.
7. **Nobody defined what "killed" means.** All four make 2026-11-30 arrive;
   none says who stops the containers, where bronze goes, or who cancels the
   €5. A kill that deletes the archive destroys the only irreproducible thing
   in the project; a kill that keeps paying is not a kill.
8. **The contact address is an unmanaged asset.** `LONGSERIES_CONTACT` is in
   the User-Agent as the station-5 withdrawal mitigation, so a TSO's "please
   stop" arrives there — and it must survive a relocation, a phone change and
   a carrier change. Nobody proposed the annual drill that proves the alert
   channel still reaches him: stop a collector for a day, confirm the mail
   arrives.
9. **The host does not exist.** Every design proposed 13–30 hours of build
   before the ninety minutes that would produce the first real operating
   evidence — the failure each of them accuses the others of.

## 6. Provenance

Four designers, opposed stances, one brief: **CLI-first and dependency-free**
(six commands, healthchecks the only push channel, no daemon beyond the
scheduler); **a generator, not a server** (a pure function over the store
writing static files, delivered rather than hosted); **push, do not pull**
(artefacts arrive; almost no surface to visit); **subtract** (the real risks
are elsewhere). One critic attacked all four against the repository, killed
four proposals, upheld three, and found the gaps in §5.
